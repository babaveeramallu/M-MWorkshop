CYBRSLC&CDRU OFFLINE CHAOS - V5
==========================

TRANSFER
Before replacing an older CYBRSLC-only build, remove its persistence entries
using that old EXE. The renamed build uses different Run/task names and marker
folders; it does not migrate or remove the old entries. Preserve old evidence
only as needed, or restore the clean VM snapshot before installing this build.
Branding and marker strings use CYBRSLC&CDRU. YARA rule identifiers instead use
CYBRSLC_CDRU because ampersands are not valid in YARA identifiers.
Quote paths and names containing ampersands in shell commands.
Close the old demo in the guest. Copy the ENTIRE updated bin folder to:
C:\Workshops\Simulator\bin
Include Workers and all six EXEs. Remove the temporary host share afterward.
Keep guest networking disabled. Run as an ordinary user inside the lab VM:
C:\Workshops\Simulator\bin\DoNtStopMePorfavor.exe

Confirm footer: CYBRSLC&CDRU_BENIGN_MEME_DEMO_V5 | 45-second repeat
If it says V2/V3/V4 or shows the old browser-search UI, you are running an old copy.

BEHAVIOR AFTER CONSENT
- At most five owned popups: three meme windows, fake terminal, fake Notepad.
- Eight supplied images embedded in the EXE plus two original rendered cards:
  a McDonald's job-application parody and "PUT THE FRIES IN THE BAG".
  No real application, form, personal
  data collection, affiliation, or external download.
- The parody card appears after the intro and then joins the normal image cycle.
- Intro finishes typing; then a 45-second timer disposes the old demo batch
  and shows FIVE fresh scattered windows, including replacements for closed ones.
  The first repeat is 45 seconds AFTER intro completion.
- This is not an auto-stop. Content continues until manual Stop.
- Real Notepad and Calculator receive one launch attempt each, NEVER per cycle.
- No real scripts, global keystrokes, document edits, browser activity, or downloads.
- Popup X closes it until the next batch. Stop ALL / controller Stop & Exit ends
  repetition permanently. Each batch has at most five demo popups.
- Popups start across four corners and the center of the guest working area,
  with small random offsets. Every 45-second repeat shows a fresh demo batch.
  Bounds stay within the usable desktop, excluding the taskbar.
  No continuous chasing, topmost forcing, or movement of real app windows.
- Minimize controller to tray; double-click the icon to restore it.
- Controller Stop/X/Esc, popup Stop ALL/Esc, or tray Stop ends the demo.
- Real Notepad/Calculator stay user-controlled and are not killed by Stop.

OPTIONAL REAL PERSISTENCE LAB - DISPOSABLE VM ONLY
Default startup and "I agree - start offline chaos" do NOT install persistence.
Use "Persistence lab..." > "Install (VM only)" and confirm the separate prompt.
This creates REAL, visible entries for the current user only:
- Registry: HKCU\Software\Microsoft\Windows\CurrentVersion\Run
  Value: CYBRSLC&CDRU Lab Marker
  Command: "<full path to DoNtStopMePorfavor.exe>" --lab-marker registry
- Task Scheduler Library: CYBRSLC&CDRU-Lab-Marker-<current-user SID>
  Action: the same EXE with --lab-marker task
  First trigger: approximately one minute after installation; every five minutes
  afterward, only while this user is signed in. Least privilege, no password
  stored, no elevation, no hidden task, no self-repair. One-minute execution cap.
Windows manages the task's backing registry state; do not edit TaskCache keys.
The Run entry is processed at a later Windows sign-in, not at installation.
Windows startup settings/policy can delay or disable it; do not bypass protections.

Both entry points ONLY overwrite their own small timestamp text file:
%LOCALAPPDATA%\CYBRSLC&CDRU\PersistenceLab\registry-last-run.txt
%LOCALAPPDATA%\CYBRSLC&CDRU\PersistenceLab\task-last-run.txt
They never open the popup demo, launch workers/apps, or access the network.
Use Registry Editor, Task Scheduler, and ProcMon to inspect the real artifacts.
The status display reports entry presence, not proof that triggers have run.

Stop & Exit stops the popup demo, NOT the separately installed lab entries.
Remove them with "Persistence lab..." > "Remove lab entries" BEFORE moving or
deleting the EXE. Removal verifies the expected marker command and refuses
conflicting entries. Existing entries are never overwritten by Install.
If registration fails, the matching Run value is rolled back; inspect status
and any error before retrying. Do not disable protections to force installation.
Cleanup without opening the demo (PowerShell):
  & .\DoNtStopMePorfavor.exe --remove-lab-persistence
For the exit code, use Start-Process with -Wait -PassThru. Success is exit code 0.
If the EXE was moved/deleted, manually remove ONLY the named lab Run value and
named task after inspecting their commands. Do not delete the whole Run key.
Marker text files remain as evidence; delete those two specific files if desired.
Take a VM snapshot before installation and revert it after the exercise.

OPTIONAL VISIBLE KEYBOARD EXERCISE
Open "Keyboard lab..." separately from the popup or persistence exercises.
Capture starts OFF. Check the consent box and type DUMMY text in its input box.
Only that box's character events are displayed (UTC timestamp, character/code).
This is not system-wide keylogging: no hooks, polling, other apps, clipboard
reads, automatic file writes, network, or persistence for keyboard capture.
Navigation/modifier keys are not a full physical-key trace; this demonstrates
WinForms character input only. Keyboard shortcuts in the input box are disabled.
The visible log retains the latest 500 events; input text is capped at 2000 chars.
Stop or switching to another window disables capture. Resume requires opt-in.
Clear stops capture and clears input/log memory. Close does the same.
Export log explicitly saves a user-chosen text file and confirms its path.
Clear/Close do not delete previously exported files; remove those separately.
Never enter passwords or personal data, even in this VM exercise.

SOUND
"Enable quiet goofy sound" starts UNCHECKED.
It uses a short original synthesized 0.6-second wobble, not a downloaded or
recorded "Fahahh" voice clip. It plays at sequence start if enabled, then at
45-second repeats. Uncheck to stop playback immediately; Stop also cancels sound.
Guest audio must work, and actual loudness depends on your speakers/volume.
Start with low host/guest volume. No sound loops, flashing, or surprise audio.

WORKER DIAGNOSTICS - DON'T GUESS FROM NAMES
After consent the controller starts:
FakeUpdate.exe, MemeWroker.exe, SnackScaner.exe,
svch0st.exe (zero), Isass.exe (capital i), csrsss.exe (extra s).
These are labeled lab workers, not Windows components.

Controller's persistent worker panel shows:
- Filename and PID
- RUNNING or EXITED with exit code
- READY handshake or captured startup error
- Missing-folder and process-launch errors

A successful Process.Start is NOT by itself a successful worker startup.
READY indicates the worker reached its wait/hash loop. A process can exit later;
check the current RUNNING/EXITED state too. No automatic retries or respawns.
If startup fails, copy/report the exact panel text; do not disable protection.

Task Manager > Details > right-click column headers > Select columns:
Command line, Image path name, PID.
Match PIDs from the controller, then inspect:
- Image path under guest-local Simulator\bin\Workers.
- --cybrslc-demo command-line marker.
- Processes-tab descriptions match each executable name, not a shared label.
- Properties > Details: Company CYBRSLC&CDRU Workshop; Product CYBRSLC&CDRU offline
  simulation; Comments identify the exercise as not a Windows component.
- Process Explorer parent: DoNtStopMePorfavor.exe.
Task Manager's Processes tab may group children under the controller.
Never end genuine Windows processes because their names look similar.

Workers wait most of the time and hash a 32-byte in-memory state approximately
once per second. Low or rounded-to-zero CPU is expected. They do not write files,
use networking, create scheduled tasks, or install persistence.
They signal READY on stdout; startup errors are captured from stderr.
Stop signals them to exit. They also monitor the actual controller process handle
so ending the controller should terminate them within roughly 1-2 seconds on a
responsive machine. This behavior requires guest validation.
Ending an individual worker does not restart it.
Normal Windows/app runtime artifacts may still be created.

BUILD AND TEST
Build-Prank.ps1 validates and embeds images from Meems, builds the controller,
includes LabPersistence.cs, and builds six workers.
Approved scripts only; do not change policy to force it.
Original Build.ps1/Test-Simulator.ps1 refer to the OLD console sample.
Do not use the old direct compiler command; it omits embedded resources.

Test-Workers.ps1 and Test-Prank.ps1 are not included in this source package.
Use Test-Persistence.ps1 for the available automated checks and the acceptance
checklists below for worker lifecycle, popup replacement, images, and sound.
Host compilation/static checks do not replace interactive guest lifecycle tests.
Updated worker file version: 1.1.0.0. A worker with no READY after ten seconds is
flagged as slow or potentially stale, not automatically assumed broken.

Persistence checks (Windows PowerShell 5.1, after Build-Prank.ps1):
  .\Test-Persistence.ps1
Default tests validate task XML through Windows without registering it, check
marker-only arguments/ownership guards, and instantiate hidden controls to check
existing defaults. They do NOT install persistence or write marker files.
If Windows denies executable launch, do not disable protection or change policy.
For explicitly limited validation only:
  .\Test-Persistence.ps1 -DefinitionOnly
This skips executable launch tests and all installation/execution checks; a pass
does NOT establish that the EXE or its persistence entry points can actually run.
ONLY INSIDE THE DISPOSABLE VM:
  .\Test-Persistence.ps1 -InstallInDisposableVm
This explicitly installs real entries, tests duplicate refusal, executes both
marker modes (including via Scheduler), and removes the entries in finally.
It retains marker evidence and refuses to start with existing named lab entries.
It does not prove Windows logon dispatch or the recurring timer: test those below.
The duplicate-install check deliberately calls Install twice and must recognize
the expected "An entry already exists" rejection. Older Test-Persistence.ps1
copies incorrectly failed here because PowerShell wraps reflection exceptions.
Copy the updated test script and rerun; no EXE rebuild is needed for this fix.
The test's finally block attempts cleanup even after failure. Confirm both lab
entries are absent in the persistence controls before rerunning a failed test.
